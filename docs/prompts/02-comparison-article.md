# STEP2: 比較記事を生成する

元のプロンプトは Markdown 本文を出力させるものでしたが、
このリポジトリでは **YAML を出力させて `data/` に貼る**形にしています。

理由は3つです。

- リンクの位置を毎回考えなくて済む（テンプレート側で固定される）
- 比較表・回遊・Pinterest画像・X投稿文が、同じデータから自動で作られる
- `scripts/validate.py` で型と表現を機械的にチェックできる

---

## 投げるプロンプト

`[  ]` の部分を埋めて、そのまま Claude に貼ってください。

````
あなたは、実際にその商品を使ったことがあるレビュアーです。
これから、比較記事のもとになる構造化データ（YAML）を作ってもらいます。

ジャンル：[ジャンル名]
狙うキーワード：[メインキーワード]
想定読者：[誰が何に困っているか]
比べる商品：[3つから5つ。商品名・ASIN・価格・主な仕様を貼る]

各商品について、私が集めたレビューを渡します。

（★4〜5のレビューを3件）
（★1〜2のレビューを3件）

[商品名2]
（同上）
---ここまで---

次の2つのYAMLブロックを出力してください。説明文は不要です。

### ブロック1：products.yml に追記する商品データ

```yaml
- slug: "英数字とハイフンのみ"
  asin: "[ASIN]"
  title: "[商品名]"
  brand: "[ブランド]"
  category: "[カテゴリ]"
  tags: ["", "", ""]
  price_range: "3,000〜4,500円"     # 金額そのものではなく価格帯で書く
  rating: 3.8
  image: ""
  specs:                            # 比較表の列になる。全商品で同じキーを使うこと
    厚み: "5cm"
    素材: ""
    重量: ""
  summary: "1行。どんな人の何を解決するか"
  pros:
    - "良い評価のレビューから、具体的な事実を2〜3個"
  cons:
    - "低い評価のレビューから、共通する不満を2個以上。必ず書くこと"
  best_for: "向いている人"
  stance: "researched"              # 実機を使っていない場合。使ったなら owned にする
  own_note: ""                      # researched のときは必ず空。owned のときだけ私が自分で書きます
  evidence:                         # researched のときは必須
    checked_at: "[今日の日付 YYYY-MM-DD]"
    review_count: 0                 # 確認したレビュー件数
    sources:
      - "メーカー公式の仕様表"
      - "Amazonカスタマーレビュー（★1〜2を中心に確認）"
  review: |
    2〜3段落。レビューの不満に触れ、それが商品の問題なのか
    使い方や環境の問題なのかを切り分けて書く。
```

### ブロック2：comparisons.yml に追記する記事データ

```yaml
- slug: "英数字とハイフンのみ"
  title: "[キーワードを含む見出し]"
  keyword: "[メインキーワード]"
  category: "[カテゴリ]"
  updated: "[今日の日付 YYYY-MM-DD]"

  basis: |
    何をもとに比べたのかを2〜3行。実機を使っていないならそう書く。
    どの観点は評価できて、どの観点は評価していないのかを明示する。

  scene: |
    読者がいま困っている場面を2〜3行で描写する。
    商品の話はまだしない。

  not_for:                          # 先に外す。3つ程度
    - "この記事が向いていない人と、その理由"

  criteria:                         # 必ず3つ
    - name: "基準の名前（数値やサイズで比べられるもの）"
      why: "なぜこれを見るのか"
      check: "読者が自分で確認する具体的な方法"

  table_columns: ["厚み", "素材", "重量"]   # specs のキーと一致させる

  items:
    - slug: "[商品のslug]"
      for_whom: "向いている人"
      not_for_whom: "向いていない人。必ず書くこと"
      comment: "1〜2行の短評"

  complaints:                       # 低い評価のレビューから共通する不満を拾う
    - complaint: "レビューで多かった不満"
      fix: "その対処法。商品を貶めずに書く"

  situations:                       # 状況別のおすすめ。記事の最後で判断を固める
    - situation: "読者の状況"
      slug: "[商品のslug]"
      reason: "なぜこの状況ならこれなのか"

  first_steps:                      # 買ったあと、最初にやること
    - "具体的な行動"

  closing: |
    2〜3行。売り込まずに締める。

  related: []                       # ここは空でよい（STEP4で埋めます）
```

## ルール

・すべてを良いと書かないこと。合わない場面を必ず書くこと
・低い評価のレビューから、共通する不満を必ず拾うこと
・調べれば出てくる一般論だけで終わらせないこと
・「絶対」「必ず」「誰でも」「100%」「確実に」「最安値」は使わないこと
・効果や結果を断定しないこと。医薬品的な表現（治る・完治）は使わないこと
・他社商品を貶める表現は使わないこと
・価格や仕様は、変更される可能性がある前提で書くこと
・整いすぎた文章にせず、文の長さに揺らぎを作ること
・own_note は必ず空にすること

実機を使っていない（stance: researched）場合の書き方
・「使ってみた」「実際に使って」「私は」など、自分で使ったことになる表現を使わないこと
・代わりに「レビューでは〜という声が多い」「仕様上は〜」のように、
　情報の出どころが分かる形で書くこと
・使ってみないと分からないこと（座り心地、音の質、肌ざわり）は評価せず、
　「この記事では評価していない」と書くこと
・数値やサイズなど、仕様表で確認できることを比較の軸にすること
````

## 貼り付けたあとにやること

```bash
# 1. 出力されたYAMLを data/products.yml と data/comparisons.yml に追記する

# 2. stance を確認する
#    使った商品 → stance: owned にして own_note を1〜3行書く
#    使っていない → stance: researched のまま。evidence を埋める

# 3. チェックして生成する
python scripts/validate.py
python scripts/build_site.py
python -m http.server -d public 8000
```

## 2つのモード

| | stance: owned | stance: researched |
| --- | --- | --- |
| 前提 | 実際に使った | 使っていない |
| 必須 | `own_note`（気づいた一言1〜3行） | `evidence`（調べた日・件数・出どころ） |
| 記事の表示 | 「実機を使用」バッジ＋使ってみての枠 | 「実機未使用」バッジ＋根拠の1行 |
| 書ける内容 | 体験に基づく評価 | 仕様とレビューの整理 |
| 書けない内容 | — | 座り心地・音質・肌ざわりなど、使わないと分からないこと |

`owned` の `own_note` に書くのは、レビューを読んでも分からないことです。

- 実際に測った数値（「座面が実測で3cm上がった」）
- 使ってみて予想と違ったこと（「腰より、座り直す回数が減った」）
- 買う前に確認すべきだったこと（「先に机との差を測るべきだった」）

`researched` で価値を出すのは、**レビューの読み込みの深さ**です。

- ★1〜2を30件以上読んで、**同じ不満が何件出ているか**を数える
- その不満が「商品の問題」か「使い方・環境の問題」かを切り分ける
- 仕様表の数値を横に並べて、**メーカーが揃えて書いていない項目**を揃える
  （「明るさ◯lx」の測定距離、「耐荷重◯kg」の取り付け幅など）

3つ目が特に効きます。仕様の表記条件が揃っていないカテゴリは、
それを揃えるだけで既存の記事より価値が出ます。

**どちらのモードでも、使っていない商品を使ったように書くことはできません。**
`validate.py` が体験表現を検出してエラーにします。
